编排 知识 治理 可观测 基础设施

一、双层编排：嵌套，不是串行

这是本项目最容易误解的一处。Temporal 语义的持久化外壳与推理图是嵌套关系： 外层负责「跨小时~天级的状态、超时、审批挂起」，内层负责「毫秒~秒级的推理」。 推理图做完就返回，不持有跨重启状态。

① 外层 · 持久化工作流（temporal/workflow.py）

状态机 · 审批挂起/恢复 · 超时默认拒绝 · 幂等键落库 · 职责分离

② 内层 · 推理图（graph/pipeline.py）

一次 Activity 内运行：6 个节点，手写执行器与 LangGraph 执行器共用同一批节点函数

normalize_alarm → collect_topology → collect_logs → reason → propose → supervise

工具调用 → 治理拦截器 → 高风险动作挂起 WAITING_APPROVAL → 审批信号 → 受治理执行

二、横切能力：不是流水线阶段

下面四项同时服务于编排层与推理层，任何一层都可以调用它们，它们不参与"第几步"的顺序。

Ontology · 只读 TBox 领域词表唯一定义一次，被三处消费：Prompt 渲染 · 公理校验 · Agent 输出校验
Governance · 工具拦截器 风险分级 · RBAC · 策略检查位于重试循环之外
Observability · 父子树 Span contextvars 维护 Span 栈 · 异常也落盘 · 跨重启可回读
Memory / Persistence Episodic 记忆 + DocumentStore（workflows / traces / 幂等 / badcases）
Resilience · 限流缓存 令牌桶 · TTL+LRU 缓存 · 资源锁 · 熔断
Protocol · A2A / MCP AgentCard 与 MCP 工具目录从注册表动态生成

三、工具调用链：10 步，顺序即设计

治理检查必须发生在重试循环之外。否则策略拒绝会被当成瞬时故障重试 3 次， 最终报 ToolError 而不是 ToolPolicyDenied—— 运维看到的是"工具不稳定"，而不是"有人试图越权"。

  1. 存在性检查 未注册 → ToolNotFound，不做隐式放行
  2. 熔断检查 连续失败达阈值 → CircuitOpen
  3. 治理检查 策略拒绝一次抛出，计数进 policy_denials 并写 BadCase
  4. 权限检查 required_permission ∈ principal 权限集合
  5. 出站限流 令牌桶，按 tool:{name} 隔离
  6. 幂等查询 idempotency_key 命中即返回，handler 不再执行
  7. 结果缓存 cacheable 工具按 payload 稳定哈希
  8. 资源锁 resource_field 指定的资源互斥（FIFO + 超时）
  9. 重试循环 仅对 TransientToolError 重试；PermanentToolError 立即失败
  10. 失败归档 最终失败写 BadCase，构成闭环输入

五、真实调用树（aio-agentos demo）

实测 14 个 Span、深度 4、2 个根节点。aio-agentos check 会断言 max_depth >= 2——扁平 Trace 无法回答"这个 LLM 调用是哪个 Agent 发起的"。

- [workflow]    workflow.run (5.8ms)
  - [graph_node] graph.run (5.6ms)
    - [agent]      agent.run (1.6ms)   ← alarm
      - [llm]      llm.complete (1.0ms)
    - [agent]      agent.run (1.6ms)   ← topology
      - [tool]     tool.invoke (0.1ms)
    - [agent]      agent.run (0.0ms)   ← log
    - [agent]      agent.run (0.9ms)   ← reasoning
      - [llm]      llm.complete (0.3ms)
    - [agent]      agent.run (0.4ms)   ← remediation
      - [llm]      llm.complete (0.1ms)
    - [governance] graph.supervise (0.0ms)
- [activity]   workflow.remediation (0.4ms)   ← 第二个根：审批后才发生
  - [tool]     tool.invoke (0.1ms)

为什么有两个根？workflow.run 覆盖推理阶段，它在 WAITING_APPROVAL 时已经返回； 审批与执行发生在那之后，不在它的上下文里。Span 栈如实反映真实嵌套，而不是为了让树好看而强行套一层。

六、状态所有权：三套状态，各归其位

状态存活范围是否持久化归属
WorkflowState 跨小时~天，跨重启 是（workflows collection） 持久化编排字段的唯一事实源
AgentContext 单次 Agent 调用 否 用完即弃，不跨 Agent 复用
IncidentGraphState 一次推理 Activity 内 否 推理中间结果，返回后合并进 WorkflowState

为什么审批状态必须持久化：WAITING_APPROVAL 是唯一会长时间挂起的状态。 如果它只在内存里，服务重启后审批人点击批准会得到 404「工作流不存在」—— 故障无人处理，甚至可能被重复提交导致服务被重启两次。

七、治理：四层机械保证

「模型会不会给出一个危险动作并真的执行」这个问题，答案不是"提示词里写了不要这么做"，而是四层可执行约束。

① 词表约束 越界动作收敛到 collect_more_evidence（无副作用出口），并标记 ontology_violation
② 风险驱动审批门 由 ToolSpec.risk_level 推导，不是 action == "restart_service" 这类启发式
③ 拒绝不被重试掩盖 策略检查在重试循环之外；拒绝时 handler 一次都没被调用
④ 职责分离 approver 有 approval:decide 但没有 tool:high——即使已批准也不能自己执行

八、本体驱动的三处消费

领域词表在 ontology/domain.py 唯一定义一次，然后被三个地方共同消费。 三者任一单独存在都不够：只有 Prompt 约束，模型仍可能越界；只有输出校验，模型会浪费 token； 只有公理校验，错误发现得太晚。

#消费点作用落点
①Prompt 渲染把允许取值注入提示词，从源头约束输出空间root_causes_for_prompt()
②本体公理校验在执行前拦截越界输出，越界即失败graph.supervise 节点
③Agent 输出校验越界值收敛到安全出口，并标记 ontology_violationis_valid_root_cause()
